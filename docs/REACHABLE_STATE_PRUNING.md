# 位置ごとの到達可能状態だけを処理する版 — 調査記録

対象: `src/experiments/moto_probe_mph_inplace_reachable.cpp`
**判定: 不採用。** 正しくしても効果が出ない（後述）。

## 目的

`src/moto_probe_mph_inplace.cpp` は各セル位置 p で**全状態ブロックを無条件に走査**する。
到達していない（値が 0 の）ブロックを飛ばせば、計算量を削減できるはずだという仮説を検証した。

## 設計

元実装を `#define main` で丸ごと取り込み、`ReachablePathCounter` だけを新規定義する。
到達可能性を2層で管理する。

| 層 | 配列 | 単位 | 役割 |
|---|---|---|---|
| 1 | `reachableBlocks[codeSizeL()]` | block（左 mate 固定の状態群） | 「この block は非ゼロ値を持つか」 |
| 2 | `reachableGroups[cols × numGroups]` | 位置 p × group | 実際の枝刈り判定 |

- block が初めて非ゼロを受け取った時点で、**全位置 p について**その block の
  group フラグを立てる（`activateBlock`）。
- `value` は DP 中に減少しない（減算が存在しない）ため、フラグは単調増加。
- 遅延値（deferred）を書き込むときは、`activateDeferredConsumers` が
  その値を消費しうる main 状態の block を先回りして活性化する。
- 出力メトリクスに `reachable blocks` と、実カウンタ版の `state visits` を追加。

## 切り分けの過程

| 実験 | 結果 | 分かったこと |
|---|---|---|
| group 枝刈りのみ無効化（`if (reachableGroups…)` → `if (true)`） | n=12 まで完全一致 | **block 活性化ロジック自体は正しい** |
| 各位置で `reachableBlocks` から group 集合を再計算 | 変化なし | group フラグの陳腐化が原因ではない |
| `isMainState` を正しい走査順に修正 | **1桁も変化なし** | ここは原因ではない |

`isMainState` は元々、mate を位置 0 → cols-1 の**昇順**に走査し、分割点も
`leftWidth()` だった。正しくは位置 cols-1 → 0 の**降順**、分割点は
`rightWidth()`（左部が高位・右部が低位）。バグではあるが、有効性には影響していなかった。

### 真因

`updateBlockAtPosition` の NN 枝の `c += d` と、NL/NR 枝の `c += cc; c += d;` が、
**自ブロックに非ゼロを書き込むのに `activateBlock` を呼んでいない**。

該当 block は「同じ group に属する別 block が到達済み」という理由だけで処理されている
（便乗）ため `reachableBlocks` に入らず、後続位置で group フラグが落ちた瞬間に脱落する。

switch の直後に1行足すと直る：

```cpp
const Code blockIndex = blockIndexFor(block.mateL);   // 関数先頭
...
            default:
                break;
            }
            if (c != 0) {
                activateBlock(blockIndex);            // switch の直後
            }
```

これで **n=4〜14 までオリジナルと完全一致** した
（n=13 = 69450664761521361664274701548907358996488）。

### 未解決: SIGSEGV

修正版でも **n=13 と n=15 でセグメンテーションフォルト**（未修正版は n=15）。
修正によって到達 block が増え、潜在バグを踏むようになった。
最有力は `activateDeferredConsumers` → `insertSlot` / `isMainState` /
`wc.encode(compressed)` の経路で不正なコードを生成し `deferred[]` を破壊するもの。
`NDEBUG` で assert が無効化されているため範囲外アクセスが黙って発生する。
効果が出ないと判明したため、追究はしていない。

## なぜ不採用か

**正しくしても速くならない。** n=14、1スレッドの実測：

| 指標 | オリジナル | 到達可能版（修正済み） |
|---|---:|---:|
| state visits | 114,007,950 | 111,601,859（**2.1% 減のみ**） |
| 経過時間 | 0.748 秒 | 5.013 秒（**6.7 倍遅い**） |

理由は構造的で、2つある。

1. **到達集合が序盤で飽和する。** 終了時点の到達 block 数は全 block 数に等しい
   （n=14: 1373 / 1373）。枝刈りが効くのは最初の数セルだけ。
2. **group 粒度が粗すぎる。** group 数は `1 << (leftWidth - 2)` で、
   n=14 で 32、n=18 でも 128 しかない。1つの group が巨大なため、
   ある group に1つでも到達 block があれば group 全体（＝大量の未到達 block）を
   処理することになり、block 単位の枝刈りが group 単位の実行に吸収されて消える。

参考: block 数と group 数（`scratch_blocks_probe` による実測、archive/scratch/ に退避）

| n | cols | leftWidth | rightWidth | blocks | states | groups |
|---:|---:|---:|---:|---:|---:|---:|
| 10 | 11 | 5 | 6 | 171 | 9713 | 8 |
| 12 | 13 | 6 | 7 | 483 | 71799 | 16 |
| 14 | 15 | 7 | 8 | 1373 | 542895 | 32 |
| 16 | 17 | 8 | 9 | 3923 | 4179603 | 64 |
| 18 | 19 | 9 | 10 | 11257 | 32652735 | 128 |

## 結論

この DP の状態空間は本質的に稠密で、「到達可能状態だけを処理する」アプローチは
原理的にリターンがない。n > 20 を狙う場合は、可変 limb 化やメモリ削減など
別の方向を検討すべき。
